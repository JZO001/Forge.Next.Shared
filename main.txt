Version 3.3.0.0

Add includeStackTrace option to the Protect wrappers (v3.3.0)

Expose the stack-trace omission that v3.2.0 added to ToErrorOrError on
all four Protect* wrappers in ObjectExtensions, so a caller can keep the
trace out of the error metadata without catching and converting the
exception itself. The option defaults to the earlier behaviour. Update
the tests, README and version to match.

ObjectExtensions:
- Protect<T, TResult>, ProtectDo<T>, ProtectAsync<T, TResult> and
  ProtectDoAsync<T>: new optional `bool includeStackTrace = true`
  parameter, forwarded to ToErrorOrError in the catch block. When false,
  the "stackTrace" metadata entry is omitted and only "type" and
  "message" are kept - intended for boundaries whose errors leave the
  process or reach a user or language model; log the exception itself
  where the trace is needed.
- In the async wrappers the new parameter sits after
  rethrowCancellation, so cancellationToken stays last.
- XML docs extended with the new <param>, cross-referencing
  ExceptionErrorOrExtensions.ToErrorOrError.

Tests (ObjectExtensionsTests):
- New ProtectIncludeStackTraceTest: the stack trace is in the metadata
  by default, and with includeStackTrace: false it is absent from the
  errors of all four wrappers while "type" and the message are kept.
- Protect* cref signatures updated to the new parameter lists; the async
  ones now also match the actual parameter order.

README.md:
- Updated the four Protect* signatures; the async ones now list the
  parameters in their actual order (rethrowCancellation and
  includeStackTrace before cancellationToken).
- Added a "Without the stack trace" note for the Protect* wrappers.

Project:
- Bump AssemblyVersion 3.2.0.0 -> 3.3.0.0.

Compatibility: callers using named arguments or defaults need only a
recompile. A fully positional async call that passed cancellationToken
right after rethrowCancellation no longer compiles; pass the token by
name.
